# 박스오피스 데이터 변경 검증

## ① 입력과 기준 찾기

- 저장소 루트의 [AGENTS.md](../../../AGENTS.md)를 읽고 보안·상태 구분·보고 규칙을 적용한다. [PRD.md](../../../PRD.md)의 관련 AC와 [ARCHITECTURE.md](../../../ARCHITECTURE.md)의 데이터·캐시 규칙을 변경 파일에 연결한다. DB 변경이면 [ERD.md](../../../ERD.md)와 실제 마이그레이션을 대조하여 채택된 저장 모델을 확인한다.
- 변경 diff와 호출 경로에서 입력 → 파싱 → 저장 → 집계 → 응답 중 영향받는 구간을 찾는다. 직접 수정한 함수뿐 아니라 바뀐 값을 소비하는 구간도 확인한다.
- `package.json`의 실제 scripts, 기존 테스트·fixture, 로컬 테스트 DB 구성을 확인한다. AGENTS.md의 명령어가 미정이면 등록된 것으로 가정하지 않는다. 코드·도구가 없으면 실행 불가 사유를 기록한다.
- 기대값은 요구사항과 수동 계산으로 정한다. 변경한 구현을 그대로 복제한 계산을 정답으로 사용하지 않는다. 정상 목록·정상 빈 목록·외부 오류·잘못된 숫자·부분 누락 중 변경과 관련된 입력을 선택한다.
- 기본은 비밀값 없는 fixture와 격리된 테스트 DB다. 실제 KOBIS 호출은 계약 확인이 필요한 경우에만 허용 범위·호출 한도 안에서 수행한다. 실제 DB 변경은 이 Skill 호출만으로 허가된 것이 아니므로 운영 DB에 쓰거나 데이터를 지우지 않는다.
- `KOBIS_API_KEY`와 `SUPABASE_SECRET_KEY`는 서버에서만 사용한다. `.env.local` 내용, 키가 들어 있는 URL·헤더·오류 객체를 출력·기록하지 않는다.

## ② 변경에 맞춘 검사 선택

변경에 해당하는 행을 선택하고, 다른 구간까지 영향이 전파되면 해당 검사도 추가한다. 단순한 문구·스타일 변경만 확인되면 이 절차를 종료하고 일반 작업 흐름으로 돌아간다.

| 변경 영역 | 검사할 입력·동작 | 통과 판단 기준 |
| --- | --- | --- |
| API 응답 파싱 | 정상 응답, 성공 빈 목록, HTTP 200의 오류 구조, 깨진 응답, 필수 식별자 누락 | 정상·empty·error를 구분하고 필수 구조 오류를 성공 데이터로 저장하지 않음 |
| 숫자 변환·직렬화 | `"900"`, `"1000"`, 실제 `"0"`, 빈 문자열·문자·소수·허용 범위 밖 값, JS 안전 정수 한계 초과 정수 | 900 < 1000, 합계 1900. 허용되지 않은 값은 NULL·경고이고 실제 0과 구분. 큰 정수는 정밀도 유지, JSON은 정수 문자열이며 BigInt 직렬화 오류 없음 |
| 기간 요청 매핑 | 한국 날짜 경계·전일·미래 날짜, 일간/주간/주말 요청과 실제 응답 집계 범위 | 잘못된 입력 차단, 날짜 범위 일치. 주간·주말은 어댑터 요청과 실제 응답 범위를 대조; mock만 사용했다면 실연동 확인은 별도 미실행 표시 |
| DB 저장 | 같은 응답 반복 저장, 동일 키 갱신, 영화 정보 정정, 저장 도중 오류, 값 읽기 복원 | 중복 없음, PK/FK·유니크 조건 유지, 정수 정밀도 보존. 정규화 모델은 기간·실적 교체가 원자적이며 실패 시 이전 정상 상태 유지 |
| 캐시 분기 | 유효 캐시, 없음·만료, 정상 빈 결과, 외부 실패, DB 장애, 동시 갱신 | 유효 캐시에서 외부 호출 없음. 성공만 갱신하고 빈 결과는 별도 상태·짧은 TTL. 실패 시 기존 만료 시각 유지, 허용된 오래된 캐시만 표시와 함께 제공. 중복 갱신 억제 정책 준수 |
| 지표·Top 계산 | 같은 코드의 여러 날짜, 동명·다른 코드 영화, 매출 동률, 빈 날·실패 날·필드 누락, 전체 빈 기간 | movieCd별 합산, 매출→관객→코드 순 정렬, Top 5/10 개수 준수. 누적 매출·관객 합산 금지. 결측 0 대체 금지, 지표별 유효 날짜 분모·부분 집계·전체 empty/error 구분 |
| 검색 상태에 대한 영향 | 원본 있음+검색 불일치, 원본 empty, 원본 error | 검색 결과 없음·정상 빈 응답·API 오류의 안내와 복구 동작을 구분 |

지표 검사의 작은 기준 예: 같은 영화의 유효한 두 날 매출이 900원·1,000원이고 나머지 하루가 결측이면, 기간 매출은 1,900원이고 일평균 매출은 950원이며 유효 날짜 수는 2다. 누적 수치와 결측일을 더하지 않는다. 큰 정수의 예 `"9007199254740993"`은 저장·응답 후에도 동일해야 한다.

기존 테스트가 있으면 영향받는 테스트부터 실행한다. 검사가 부족하면 위 불변식을 확인하는 최소한의 테스트를 추가한다. 실제 등록된 lint·typecheck·build 중 변경에 필요한 검사를 수행하되, 이 검사들의 성공만으로 데이터 정확성을 통과 처리하지 않는다. 입력이나 환경을 고치지 않은 채 같은 실패 명령을 반복하지 않는다.

## ③ 결과와 중단 기준

- 기대값 불일치는 **실패**다. 원인을 좁혀 요청 범위 내에서 수정하고 영향받는 검사만 다시 실행한다. 해결되지 않은 핵심 실패가 있으면 검증 완료로 선언하지 않는다.
- 실행 도구·키·격리 DB·필수 기준이 없거나 권한·네트워크로 실행할 수 없으면 해당 항목은 **미실행**이다. 독립적으로 가능한 fixture·정적 검사는 계속 수행하고, 부족한 근거와 다음 조치를 보고한다.
- 비밀값 노출, 운영 DB 변경 위험, 저장 모델 충돌로 안전한 검증이 불가능하면 해당 경로를 중단한다. 비밀값을 재출력하지 말고 영향·해결에 필요한 결정만 보고한다. Skill 사용을 커밋·배포·운영 데이터 수정의 허가로 해석하지 않는다.
- 필요한 검사에 모두 근거가 있고 실패·핵심 미실행이 없을 때만 이번 변경 범위의 검증 완료를 보고한다. mock 테스트 통과를 실제 API·DB 연동 통과로 확대하지 않는다.

결과는 한국어로 아래 형식에 맞춰 보고한다. 일반 모드 작업 계획과 Plan Mode 계획 결과를 구분하며 계획한 검사를 실행 결과처럼 표시하지 않는다.

| 상태 | 정의 | 반드시 포함할 근거 |
| --- | --- | --- |
| 통과 | 실제 실행·관찰한 결과가 사전에 정한 기준과 일치 | 검사 범위, 명령 또는 확인 방법, 기대값·실제값의 핵심 결과 |
| 실패 | 검사를 실행했으나 기준 불일치 또는 테스트 실패가 발생 | 재현 입력, 기대값·실제값, 영향과 남은 조치. 비밀값은 제외 |
| 미실행 | 검사를 실행하지 못했거나 결과를 관찰하지 못함 | 미실행 사유, 검증 공백, 실행에 필요한 조건 |

최종 보고에는 변경 파일·연결된 AC·검사별 상태·남은 위험을 간결하게 적는다. 해당 없는 검사는 검사 선택에서 제외하고 이유를 밝히며, 미실행을 통과로 합산하지 않는다. 테스트 도구나 코드가 없는 문서 작성 단계라면 문서 구조 검토와 애플리케이션 검증을 분리해서 보고한다.
